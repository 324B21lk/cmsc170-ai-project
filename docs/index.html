THE PATHFINDING PROBLEM

Finding Paths,
Comparing Methods

In grid-based pathfinding, an algorithm must travel from a starting cell to a goal without leaving the map or crossing obstacles. Each map identifies which cells can be entered and which ones are blocked.

What are we trying to solve?

For each test case, our program is given a two-dimensional grid map, a starting cell, and a goal cell. The task is to find a valid path from the starting point to the destination while staying within the map boundaries and avoiding obstacles.

All three algorithms follow the same movement rules: they can move up, down, left, or right, but not diagonally. Each move has a cost of one unit, ensuring that BFS, DFS, and A* solve the same pathfinding problem under consistent conditions.

Why compare the three methods?

Finding a path does not always mean finding the shortest route. Different search algorithms use different strategies, which can affect the path length, number of nodes explored, and execution time.

Pathfinding is used in GPS navigation, robotics, video games, and delivery systems, where finding efficient routes can save time and resources. Choosing
the right algorithm can therefore make a difference in real-world applications.

By testing BFS, DFS, and A* on the same maps and start–goal pairs, we can compare their performance and better understand how their search strategies affect the results.

ABOUT THE PROVIDED DISTANCES

The DAO scenario files contain reference path lengths for the benchmark's octile movement rules. Because our implementations allow only four directions, we calculate path lengths from the routes returned by our own algorithms instead of using the provided values as four-directional answers.

THE SEARCH METHODS

Three strategies.
One set of rules.

Each method takes the same input: a grid, a start position, and a goal position. What changes is how it chooses the next cell to explore. All three record parents to reconstruct a path and return success, path, path length, explored-node count, and execution time.

BFS
UNINFORMED SEARCH · LEVEL BY LEVEL

Breadth-First Search

QueueFirst in, first out

BFS starts at the given position and explores nearby cells before moving farther away. The implementation uses Python's deque as a queue. Each valid walkable neighbor is marked visited as soon as it is added, preventing the same cell from entering the queue more than once.

As BFS visits new cells, it records which earlier cell led to each one. When the goal is reached, those parent links are followed backward and reversed to produce the route from start to goal. Because every allowed move has the same cost, the first route BFS finds to the goal is a shortest one.

IN THE CODE · bfs.py
queue = deque([start])
current = queue.popleft()

Expand the earliest queued position, then append its unvisited neighbors.

DFS
UNINFORMED SEARCH · DEEP EXPLORATION

Depth-First Search

StackLast in, first out

DFS follows one branch of the search space as far as it can before trying alternatives. Our version uses a Python list as a stack. Each entry stores a position and the cell that led to it; pop() removes the most recently added entry. A position is marked visited when it is removed from the stack, and already visited entries are skipped.

When DFS reaches the goal, it traces recorded parents to recover the route. It can find a valid solution, but it does not promise the shortest one: a direction chosen early in the search can lead to a long detour, even if the goal is nearby.

IN THE CODE · dfs.py
stack = [(start, None)]
current, previous = stack.pop()

Follow the most recently added position, while skipping cells visited earlier.

A*
INFORMED SEARCH · HEURISTIC GUIDANCE

A* Search

Priority queueLowest estimated total cost

A* ranks candidate positions using two quantities: the cost already spent reaching a cell and an estimate of the remaining distance to the goal. Our implementation uses heapq to choose the lowest-priority entry, stores the best known cost in g_scores, and updates parents whenever a cheaper route to a position is found.

For this grid, the heuristic is Manhattan distance which is the absolute difference between the row coordinates plus the absolute difference between the columns. Because movement is restricted to four directions with cost 1 per step, this estimate does not exceed the true remaining cost. Our A* implementation can therefore find shortest paths under these rules.

PRIORITY CALCULATIONf(n) = g(n) + h(n)
g(n) cost from starth(n) Manhattan estimate to goal
IN THE CODE · astar.py
tentative_g = current_g + 1
h_score = manhattan_distance(neighbor, goal)
f_score = tentative_g + h_score

The priority queue considers both the cost so far and the estimated distance remaining.

WHAT STAYS CONSTANT

Every implementation searches the same walkable terrain, follows the same four-directional movement rules, uses unit movement cost, and works with the same start–goal scenarios. Only the search strategy differs.
